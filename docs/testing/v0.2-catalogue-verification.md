# V0.2 catalogue verification — INV-001

Branch `feature/v0.2-inventory`, [issue #3](https://github.com/GnaneswarRaju/SriNidhi/issues/3). This is the catalogue slice, not completion of V0.2 or a production release.

## Verification scope

- SQL contracts run through PGlite/PostgreSQL with an Auth shim: exact decimals, rejected invalid values, atomic reference rollback, normalized references, duplicate SKU, idempotent creates after edits, prefix escaping, same-name keyset pagination, inactive filter, immutable unit, optimistic version conflicts, tenant/role/revocation restrictions and denied direct/anonymous access.
- Flutter contracts: exact BigInt values and validation, secure UUID format, responsive catalogue/forms at 320/390/834/1440, 200% text at 320, read-only role UI, unchanged-ID network retry, exact string payload, search/pagination reset and load retry. Foundation regression tests remain enabled.
- Real Supabase/PostgREST CI adds parallel create retries, parallel edit conflict, maximum price precision, list/search/deactivation, duplicate rollback, current-role permission enforcement, membership revocation and audit counts to the existing Auth integration check. The script rejects non-loopback hosts and creates disposable fixtures only.
- Manual renders use synthetic fixtures, not hosted data. Hosted app verification reads the actual Owner catalogue and validates the empty form without inserting fake stock/products.

## Results

Local verification completed on 2026-09-26 with Flutter 3.47.5 / Dart 3.13.4. Formatting and static analysis passed, all 25 Flutter tests passed with coverage enabled, both PostgreSQL SQL contracts passed, and the connected release web build passed. Remote CI evidence is recorded separately below; no pending check is claimed as passing.

- Nine catalogue widget cases passed, including 200% text and stable-ID retries. Three render cases passed; all six PNGs inspected.
- Development migration `20260926050304_product_catalogue.sql` applied successfully. All four public catalogue tables have RLS and deny anonymous reads and direct authenticated writes. The uncommitted CLI filename was aligned to the first hosted migration version without SQL changes.
- Advisors: the private request table intentionally has RLS and no policy/grants (deny all clients); [RLS policy notice](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). New indexes report [unused-index information](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index) on the empty development catalogue and are retained for access/FK workloads. Existing [leaked-password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) is disabled and requires Pro; no plan change was made. Track as a production gate, not a migration regression.
- The configured release app restored the user's existing Owner session, displayed Sri Nidhi Hardware / Main branch, loaded the hosted empty catalogue and opened the product form. Submitting empty fields showed name/SKU/price errors. Cancel returned to the catalogue. Browser warning/error logs were empty. A server count confirmed zero products before this form check; no fake hosted product was inserted.
- The web compiler repeats the foundation's optional Cupertino font warning; this app uses verified Material icons. Wasm dry run passed; the tested release target is JavaScript. Native platforms remain unverified.
